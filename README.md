# gornitsa.games

Сайт студии мобильных игр «Горница» на русском и английском: главная, страницы игр студии, поддержка, политика конфиденциальности и страница 404. Сайт статический: HTML, CSS и немного JavaScript, без сборщиков и зависимостей. Шрифты (Kurale и Onest, лицензия SIL OFL) раздаются с того же сервера, поэтому сайт не обращается к Google и другим внешним сервисам. В репозитории шрифтов и готовых страниц нет: их скачивает `deploy/fetch-fonts.sh` и собирает `build.py`.

## Как посмотреть локально

```bash
bash deploy/fetch-fonts.sh
python3 build.py
python3 -m http.server 8000 -d site
# открыть http://localhost:8000
```

## Как поменять текст

1. Отредактируйте нужную страницу в `src/` (шапку и подвал — в `src/partials.py`). Страницы игр
   и карточки игр на главной здесь не правятся: они собираются из `store/site/` игр (см. «Страницы игр»).
2. Запустите `python3 build.py`.
3. Сделайте `git push` — через несколько минут сервер обновит сайт сам.

Стили и скрипты редактируются прямо в `site/assets/`, кроме `brand.css`: это копия
`brand/tokens.css` из устава студии [`Nefeste/gornitsa`](https://github.com/Nefeste/gornitsa)
с пометкой источника в первой строке. Цвета, шрифты и скругления меняются сначала там, потом
копия переносится сюда.

Страницы «О студии» и «Брендбук» пересказывают устав студии (`docs/01-mission.md`,
`docs/02-values.md`, `brand/README.md`). Меняется обещание или правило бренда — сначала
в уставе, потом здесь, в том же заходе.

У каждой страницы есть пара на другом языке: русская `src/support.html` и английская `src/en/support.html`. Правьте обе, а новую страницу добавьте в список `pages` в `build.py` — тогда в шапке появится переключатель языка, а в `<head>` — ссылки `hreflang`. Надписи, которые рисует скрипт (подсказки на пяльцах, кнопка «Скопировать»), — в начале `site/assets/site.js`.

## Запуск с нуля

### 1. Домен

Домен gornitsa.games регистрируется на Рег.ру. После оплаты DNS-серверы по умолчанию — ns1.reg.ru и ns2.reg.ru, их менять не нужно.

### 2. VPS

Сервер заказан в Рег.облаке (тот же аккаунт, что и домен). Подойдёт и любой другой российский провайдер:

- ОС: Ubuntu 24.04 или 26.04;
- 1 vCPU, 1–2 ГБ RAM, 10+ ГБ диска — для статического сайта этого более чем достаточно;
- локация: Москва или Санкт-Петербург;
- при создании добавьте свой публичный SSH-ключ (`~/.ssh/id_ed25519.pub`). Если ключа нет: `ssh-keygen -t ed25519`.

### 3. DNS

В личном кабинете Рег.ру: «Домены» → gornitsa.games → «DNS-серверы и управление зоной» → добавьте две записи:

| Тип | Имя | Значение |
| --- | --- | --- |
| A | @ | IP вашего VPS |
| A | www | IP вашего VPS |

Записи обычно начинают работать через 15 минут — несколько часов. Проверка: `dig +short gornitsa.games`.

### 4. Публикация исходников на GitHub

Сервер забирает сайт из репозитория, поэтому сначала отправьте код на GitHub. Репозиторий должен быть публичным (в нём нет паролей и ключей, только сайт):

```bash
git remote add origin https://github.com/Nefeste/gornitsagames.git
git push -u origin main
```

### 5. Настройка сервера одной командой

Войдите на сервер (`ssh root@IP_СЕРВЕРА` или через консоль в панели провайдера) и выполните:

```bash
curl -fsSL https://raw.githubusercontent.com/Nefeste/gornitsagames/main/deploy/bootstrap.sh | bash
```

Скрипт скачает репозиторий в `/opt/gornitsa`, поставит nginx, закроет лишние порты, выложит сайт и включит автообновление. Как только DNS начнёт указывать на сервер, он сам выпустит бесплатный сертификат Let's Encrypt и включит HTTPS.

### 6. Обновления сайта

Просто делайте `git push` в ветку `main`: сервер проверяет GitHub каждые 5 минут и выкладывает новую версию сам. Журнал: `journalctl -u gornitsa-update -n 50`. Скрипт автообновления тоже берётся из репозитория (`deploy/update-site.sh`), а при изменении `deploy/votchina/`, `deploy/nardy/`, `deploy/skazy/` или `deploy/uzory/` он доводит настройку сервера этой игры.

Настройка nginx самого сайта тоже идёт из репозитория: при изменении `deploy/nginx/` (и когда сертификат уже выпущен) `update-site.sh` запускает `deploy/nginx/apply.sh`. Тот сохраняет нынешние файлы, ставит `gornitsa.games.https.conf` как `/etc/nginx/sites-available/gornitsa.games.conf`, заголовки и места — в `/etc/nginx/snippets/gornitsa-site-*.conf`, `server_tokens off` — в `/etc/nginx/conf.d/`, проверяет `nginx -t`, перезагружает nginx и убеждается, что `https://gornitsa.games/` отвечает 200, а `http://` — 301. Что-то не так — всё возвращается как было, а в `/var/lib/gornitsa-nginx-site` пишется `failed <версия>`: эту версию скрипт больше не пробует, пока `deploy/nginx/` не поменяется снова. Блоки сертификата в конфиге — в том виде, в каком их пишет certbot, поэтому продление работает по-прежнему. Заголовки безопасности — в `headers.conf` и подключаются в каждом `location`: nginx не складывает `add_header` сервера и места, и заголовки на уровне сервера молча пропадали бы.

Если репозиторий нужен закрытым, сайт можно выкладывать со своего компьютера: `./deploy/deploy.sh IP_СЕРВЕРА` (нужен SSH-доступ пользователем deploy, его создаёт `deploy/setup-server.sh`).

## Сени — шлюз студии (отдельная машина)

Сени — шлюз, через который ИИ-сотрудники студии читают почту поддержки, отзывы RuStore и каналы и готовят черновики ответов; отправляет только владелец, с Пульта (решение — ADR 0013 в уставе Nefeste/gornitsa). Код закрытый — Nefeste/seni. Сени работают на своей машине seni.gornitsa.games, а не на машине сайта: там письма и личные данные, сайту и играм они ни к чему. Здесь лежит только установщик: закрытый репозиторий без ключа не скачать.

Новая машина (Ubuntu 24.04 или новее, Debian 12 или новее), от root:

```sh
curl -fsSL https://raw.githubusercontent.com/Nefeste/gornitsagames/main/deploy/seni-bootstrap.sh | sudo bash
```

Установщик создаёт ключ машины, показывает его (и выкладывает по адресу `http://<адрес машины>/.well-known/seni-deploy.pub`) и ждёт до часа, пока ключ добавят в Nefeste/seni → Settings → Deploy keys без права записи. Потом забирает репозиторий в `/opt/seni/repo` и запускает его `deploy/setup.sh`; дальше Сени обновляются из своего main сами. Ключи и пароли вводит владелец: `sudo seni-keys` (`docs/02-secrets.md` в Nefeste/seni).

Переезд на другую машину или компьютер (подробно — `docs/05-deploy.md` в Nefeste/seni): на старой `sudo seni-migrate export` собирает ключи, ключ доступа и базу в один файл, зашифрованный паролем; файл копируется на новую машину, и там запускается тот же установщик с `SENI_IMPORT=/root/<файл>`. Потом — A-запись `seni` на новый адрес, старую машину выключить.

## Перед публикацией игр в RuStore

- Перед выходом каждой игры добавьте в политику её раздел, как у «Вотчины»: перечень сервисов (реклама, аналитика) должен совпадать с тем, что реально встроено в игру.
- В консоли RuStore укажите ссылки: политика — https://gornitsa.games/privacy.html (для «Вотчины» можно сразу на её раздел: https://gornitsa.games/privacy.html#votchina), поддержка — https://gornitsa.games/support.html.
- Ссылка на предзаказ или карточку RuStore на странице игры и в её карточке на главной — поле `links` (и `card.links`) в `store/site/page.*.md` игры.

## Страницы игр — из `store/site/` игр

Страница каждой игры (`src/<игра>/index.html` и `src/en/<игра>/index.html`), её карточка на главной
и картинки `site/assets/games/<игра>-*` собираются из папки `store/site/` репозитория игры (ADR студии
0015; формат — устав `Nefeste/gornitsa`, `docs/08-publishing.md`, раздел «Сайт»). Здесь их руками
не правят: правка текста или снимков — PR в игру, а сайт заберёт её сам.

- Workflow «Страницы игр» (`.github/workflows/games.yml`) каждую ночь в 03:17 по Москве и по кнопке
  «Run workflow» забирает `store/` с `main` игр из `tools/games.json` (`tools/fetch-games.sh`),
  собирает страницы (`tools/games.py`), собирает сайт и проверяет ссылки и картинки (`build.py`,
  `tools/check.py`) и открывает или обновляет PR «Сайт: обновления игр» из ветки `games/sync`.
  Сливает владелец; через несколько минут сервер обновит сайт сам.
- PR всегда собирается от свежего `main`: ветка `games/sync` каждый раз строится заново — от `main`
  на момент запуска плюс один коммит, и тот же PR обновляется. Поэтому PR сам догоняет всё,
  что слито в `main` после него, — самое позднее следующей ночью, сразу — кнопкой «Run workflow».
  «Re-run» старого запуска тоже берёт свежий `main`. Если `main` ушёл вперёд прямо во время сборки,
  запуск останавливается с ошибкой и PR не трогает — нажмите «Run workflow» ещё раз. Конфликты
  в этом PR руками не разрешают: следующий запуск всё равно соберёт ветку заново.
- Из какого коммита игры взята страница и из каких картинок — в `games.lock.json` (у картинки —
  отпечаток её пикселей). Картинка, у которой пиксели не изменились, не перекодируется и в PR
  не попадает, даже если игра пересохранила файл; те, на которые больше нет ссылок, убираются.
  В описании PR — какие картинки новые и какие изменились.
- Снимки на странице игры — 540 × 960 (альбомные — 960 × 540), а по нажатию снимок открывается
  крупно поверх страницы, чтобы читался мелкий текст игры: картинка `<игра>-<снимок>-full.webp`
  до 1080 × 1920 (1920 × 1080), не больше исходника из `store/`. Просмотр — `buildZoom` в
  `site/assets/site.js`: стрелки и свайп — соседние снимки, нажатие на снимок — исходный размер,
  Esc и «Назад» телефона — закрыть. Без JS ссылка просто открывает крупную картинку.
- Игра без `store/site/page.ru.md` не трогается; игра с ошибками в папке пропускается, причина —
  в описании PR. Без `page.en.md` английская страница не меняется.
- Закрытые `nardy` и `votchina` workflow читает токеном из секрета `GAMES_READ_TOKEN`:
  fine-grained, только чтение содержимого этих двух репозиториев, действует до 28.09.2027.
  Продлевает владелец: новый токен с теми же правами (github.com → Settings → Developer settings →
  Fine-grained tokens) — и новое значение секрета в Settings → Secrets and variables → Actions.
  Без токена закрытые игры пропускаются.
- Чтобы workflow мог открыть PR, в Settings → Actions → General → Workflow permissions включено
  «Allow GitHub Actions to create and approve pull requests».
- В открытом репозитории без коммитов 60 дней GitHub выключает расписание; тогда — Actions →
  «Страницы игр» → Enable workflow.

Собрать у себя (нужны `pip install pillow pyyaml`):

```bash
bash tools/fetch-games.sh                  # закрытые игры — с GAMES_READ_TOKEN в окружении
python3 tools/games.py --src games
python3 build.py && python3 tools/check.py
python3 tools/games.py --check ../skazy    # только проверить store/site/ одной игры
```

Что остаётся за сайтом:

- Порядок игр на главной и метки `<!-- game:<игра> -->` … `<!-- /game:<игра> -->` вокруг карточки.
  Ссылки, которые знает только сайт (у «Узоров» — «Закрасить узор-пример ↑», у «Вотчины» — «Турниры»
  внизу страницы), — в `tools/games.json`.
- Новая игра: строка в `tools/games.json`, пара страниц в `pages` в `build.py`, метки карточки на
  главной, адреса в `site/sitemap.xml` и строка в `.gitignore`; дальше страница собирается сама.
- Раздел игры в политике конфиденциальности (`src/privacy.html`, `src/en/privacy.html`): есть раздел
  с `id` игры — страница ссылается на него, нет — на «Игры в разработке» (`#upcoming`). Текст раздела
  готовит игра (`store/privacy.*.md`), но живёт раздел только здесь; перед выходом игры в RuStore
  раздел должен быть.
- Страницы удаления профиля (`src/skazy/delete.html`, `src/votchina/delete.html` и английские): есть
  такая страница — на странице игры появляется ссылка «Удалить профиль». Что удаляется и сколько
  хранятся журналы и копии, сверено с серверами игр («Сказы» — `server/src/profiles.ts`,
  `retention.ts` и `docs/05-process.md`); поменялось там — поправьте здесь.
- У «Вотчины» — страница турниров `src/votchina/tournaments.html` и переадресация
  `src/votchina/privacy.html`. Онлайн-сервер, веб-версия (`/play/`) и ссылки на ход (`/g/`) с 27 сентября
  2026 года работают на https://votchina.gornitsa.games (раздел ниже); старый адрес на Cloudflare
  отключён, копия базы там удалена.

## Сервер игры «Вотчина»

Cloudflare у части российских провайдеров работает с перебоями, поэтому онлайн «Вотчины» переезжает на эту же машину: https://votchina.gornitsa.games (решение — ADR 0019 и спецификация `docs/specs/2026-09-server-ru.md` в репозитории Nefeste/votchina). Код сервера — тот же воркер, запущенный под Node; база — файл SQLite `/var/lib/votchina/votchina.db`.

Как устроено на машине (всё ставит `deploy/votchina/setup.sh`, его запускает автообновление сайта):

- служба `votchina` — `node serve.mjs` на 127.0.0.1:8787 от пользователя `votchina`; nginx отдаёт её наружу по HTTPS;
- `votchina-pull` каждые 2 минуты: забирает из закрытого репозитория ветку `vps` (сборку, прошедшую сквозной тест в CI) ключом только для чтения `/etc/votchina/deploy_key`; новая сборка — перезапуск, не ответила — возвращается прежняя. Ветка `vps-import` — выгрузка базы D1 при переезде, зашифрованная ключом машины (`/etc/votchina/age.key`);
- сертификат Let's Encrypt выпускается сам, как только A-запись `votchina` указывает на сервер;
- копия базы — раз в сутки в `/var/backups/votchina/`, хранится семь дней; журнал запросов nginx — три дня;
- открытые ключи машины: https://votchina.gornitsa.games/.well-known/votchina-deploy.pub (его добавляют в Nefeste/votchina → Settings → Deploy keys, без права записи) и `votchina-age.pub` (им задание переезда шифрует выгрузку).

Настройки службы — `/etc/votchina/env` (там же секрет `ADMIN_TOKEN` для `server/tools/delete-by-tag.sh`). Журналы: `journalctl -u votchina -u votchina-pull -n 50`.

Переезд выполнен 27 сентября 2026 года заданием «Переезд на свой сервер» в репозитории votchina: база на этой машине, версии приложения с 2.10.2 ходят сюда. Старый адрес на Cloudflare отключён, копия базы в Cloudflare D1 удалена.

## Сервер игры «Длинные нарды»

Онлайн нард — стол с другом и честные кубики — работает на этой же машине: https://nardy.gornitsa.games (решение — ADR 0018 и спецификация `docs/specs/2026-09-server-vps.md` в репозитории Nefeste/nardy). Сервер — один процесс Bun с базой SQLite `/var/lib/nardy/nardy.db`; устроен так же, как «Вотчина», только среда — Bun, а в nginx пропускается WebSocket.

Как устроено на машине (всё ставит `deploy/nardy/setup.sh`, его запускает автообновление сайта при каждом изменении `deploy/nardy/`):

- Bun — официальная сборка с GitHub, версия закреплена в `setup.sh` (та же, что в CI нард) и сверяется по SHA-256; лежит в `/opt/bun/<версия>/bun`;
- служба `nardy` — `bun server.js` на 127.0.0.1:8790 от пользователя `nardy`, память — не больше 300 МБ; nginx отдаёт её наружу по HTTPS, `/v1/live` — WebSocket;
- `nardy-pull` каждые 2 минуты: забирает из закрытого репозитория ветку `vps` (сборку, прошедшую тесты сервера в CI) ключом только для чтения `/etc/nardy/deploy_key`; новая сборка — перезапуск, не ответила на `/v1/ping` — возвращается прежняя;
- сертификат Let's Encrypt выпускается сам, как только A-запись `nardy` указывает на сервер;
- копия базы — раз в сутки в `/var/backups/nardy/`, хранится семь дней; журнал запросов nginx — три дня.

Настройки службы — `/etc/nardy/env` (там же секрет `ADMIN_TOKEN` для удаления профиля по просьбе). Журналы: `journalctl -u nardy -u nardy-pull -n 50`.

Чтобы сервер поднялся, владельцу нужно два шага:

1. У регистратора — A-запись `nardy` на тот же адрес, что у `gornitsa.games`.
2. Ключ машины — в Nefeste/nardy → Settings → Deploy keys, **без** права записи. Сам ключ: https://nardy.gornitsa.games/.well-known/nardy-deploy.pub (открывается после A-записи) или в журнале `journalctl -u gornitsa-update -n 80`.

Сборка появляется в ветке `vps` после первого слияния сервера в main нард. Проверка: `curl https://nardy.gornitsa.games/v1/ping`.

## Сервер заставы «Сказов»

Застава «Сказов» — профиль, застава друзей, лента, гостинцы, облава недели, копия хозяйства и перенос — работает на этой же машине: https://skazy.gornitsa.games (решение — ADR 0024 и раздел «Сервер» в `docs/05-process.md` репозитория Nefeste/skazy). Одиночная игра сервера не замечает; без него застава показывает «Нет связи с заставой». Сервер — один процесс Bun с базой SQLite `/var/lib/skazy/skazy.db`; устроен так же, как у нард, но без WebSocket: застава ходит обычными запросами.

Как устроено на машине (всё ставит `deploy/skazy/setup.sh`, его запускает автообновление сайта при каждом изменении `deploy/skazy/`):

- Bun — та же закреплённая версия, что у нард (`/opt/bun/<версия>/bun`, одна на обе игры);
- служба `skazy` — `bun server.js` на 127.0.0.1:8791 от пользователя `skazy`, память — не больше 300 МБ; nginx отдаёт её наружу по HTTPS и пропускает тело запроса до 260 КБ (копия хозяйства — до 256 КБ);
- `skazy-pull` каждые 2 минуты: забирает ветку `vps` (сборку, прошедшую тесты сервера в CI) ключом только для чтения `/etc/skazy/deploy_key`; новая сборка — перезапуск, не ответила на `/v1/ping` — возвращается прежняя. Рядом со сборкой может лежать `cert.sha256` — отпечаток сертификата подписи для App Links (`/.well-known/assetlinks.json`); его пишет CI «Сказов» из переменной репозитория `ANDROID_CERT_SHA256`;
- сертификат Let's Encrypt выпускается сам, как только A-запись `skazy` указывает на сервер;
- журнал запросов поддомена — без адресов (строка: время, метод, путь без `?…`, код, размер, время ответа, программа); в журнале ошибок nginx адрес остаётся; оба — три дня;
- копия базы — раз в сутки в `/var/backups/skazy/`, хранится семь дней; первого числа каждого месяца `skazy-restore-check` поднимает последнюю копию во временную папку, проверяет целостность и таблицы и пишет число строк в журнал: `journalctl -u skazy-restore-check -n 30`.

Настройки службы — `/etc/skazy/env` (там же секрет `ADMIN_TOKEN` для удаления профиля по просьбе, `server/tools/delete-by-tag.sh` в «Сказах»). Журналы: `journalctl -u skazy -u skazy-pull -n 50`.

Чтобы сервер поднялся, нужно:

1. У регистратора — A-запись `skazy` на тот же адрес, что у `gornitsa.games`.
2. Ключ машины — в Nefeste/skazy → Settings → Deploy keys, **без** права записи. Сам ключ: https://skazy.gornitsa.games/.well-known/skazy-deploy.pub (открывается после A-записи) или в журнале `journalctl -u gornitsa-update -n 80`.
3. Переменная репозитория `ANDROID_CERT_SHA256` в Nefeste/skazy — для App Links; после неё — ручной запуск задания «Сервер», чтобы `cert.sha256` попал в сборку.

Проверка: `curl https://skazy.gornitsa.games/v1/ping` и `curl https://skazy.gornitsa.games/.well-known/assetlinks.json`.

## Закрытая веб-версия «Узоров»

Проверочная сборка «Узоров» для компьютера — https://gornitsa.games/uzory/test/, только для владельца и по паролю (решение владельца от 28.09.2026; спецификация `docs/specs/2026-09-web.md` в репозитории Nefeste/uzory). Это статические файлы: службы нет, их отдаёт nginx сайта. Открытая веб-версия — позже, вместе с библиотекой игры.

Как устроено на машине (всё ставит `deploy/uzory/setup.sh`, его запускает автообновление сайта при каждом изменении `deploy/uzory/`):

- ключ шифрования машины (age) — `/etc/uzory/age.key`, открытая часть — https://gornitsa.games/.well-known/uzory-age.pub. CI «Узоров» после каждого слияния в main собирает веб-версию, шифрует её этим ключом и кладёт в ветку `vps`: репозиторий открытый, а в сборке — картинки «только для проверки», среди них картины российских музеев. Прочитать ветку может только эта машина;
- `uzory-pull` каждые 5 минут: новая сборка из ветки `vps` — расшифровка в `/opt/uzory/releases/<коммит>/test`, сжатые копии `.gz`, ссылка `current`; хранятся три последние. Не расшифровалась или неполная — остаётся прежняя;
- `uzory-nginx` пишет `/etc/nginx/snippets/gornitsa.games-uzory.conf` и один раз добавляет в конфиг сайта на сервере строку `include /etc/nginx/snippets/gornitsa.games-*.conf;` — сразу после `root` (в `deploy/nginx/gornitsa.games.conf` и `gornitsa.games.https.conf` она уже есть). Новый конфиг не прошёл `nginx -t` — возвращается прежний;
- `/uzory/test/` — только по HTTPS и только с именем и паролем из `/etc/uzory/test.htpasswd`; пока файла нет — 403 всем. Правила безопасности (CSP) — как у сайта, плюс `'wasm-unsafe-eval'`: игра рисует через WebAssembly. Поисковикам — `noindex`.

Пароль задаёт владелец — один раз, на сервере:

```bash
sudo uzory-password
```

Команда спросит имя (латиницей) и пароль (не короче 10 знаков, дважды); в файл ложится только хеш. Та же команда меняет пароль; другое имя — ещё один вход. Закрыть всем: `sudo rm /etc/uzory/test.htpasswd && sudo uzory-nginx`.

Журнал: `journalctl -u uzory-pull -n 50`. Проверка: `curl -sI https://gornitsa.games/uzory/test/` — `401` (просит пароль); пока пароля нет — `403`.
